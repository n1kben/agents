# Registers

Choose one primary register. Borrow lightly from another only when the artifact genuinely mixes media.

## Chat

Use for ordinary conversation and direct advice.

- Give the answer or current best guess first.
- Ask for a concrete example when details determine the recommendation.
- Use one small example, then explain the principle.
- Keep caveats close to the claim they qualify.
- End with the next useful action or the missing evidence.

Typical shape: “I think X is the best starting point here. For example… The reason is… If Y appears in practice, then I would reconsider.”

## Forum reply

Use for technical discussion, feedback, and disagreement.

- Acknowledge the goal or interesting question without ceremonial praise.
- Quote or name the exact claim being answered.
- State the recommendation clearly.
- Walk through one failure mode or dependency diagram.
- Distinguish personal experience from a universal law.
- Ask for complete types, a minimal example, timing, scale, or user background when needed.
- If the discussion cannot be productive, state the boundary plainly and explain what form of input would help.

For a long reply, use descriptive headings such as “History,” “Problem,” “Alternate Design,” and “Considerations.”

## Guide or tutorial

Use for teaching newcomers.

- Assume intelligence, not prior vocabulary.
- Start with something the reader can run or recognize.
- Introduce one new idea at a time.
- Use “you” and invite safe experimentation.
- Explain errors as guidance, not failure.
- Put theory, historical background, and edge cases after the basic path.
- Prefer a coherent learning sequence over exhaustive coverage.

## Technical proposal or design note

Use for APIs, languages, tools, and architecture.

- Open with the user problem and the smallest viable idea.
- Show concrete syntax, data, or workflow early.
- List constraints and cases that differ across users.
- Explain what is intentionally absent.
- Compare alternatives through invariants, failure modes, migration, tooling, and long-term cost.
- Recommend a small experiment before a general mechanism when evidence is thin.
- Specify which observation would justify expanding the design.

## Essay, release note, or talk

Use for a broad argument.

- Open with a story, familiar frustration, surprising contrast, or concrete historical scene.
- Establish stakes in human terms before technical detail.
- Build through examples and comparisons toward the thesis.
- Anticipate two or three likely reactions and answer them.
- Use diagrams, numbers, or tiny programs where they carry the argument.
- Allow occasional dry humor or self-correction.
- Close by returning to the human outcome and offering a path forward.

For talks, slide text should be much shorter than the spoken explanation. A slide may contain one question, contrast, number, or diagram.

## Short social post

Use for announcements and brief observations.

- One idea per post.
- State the practical takeaway first.
- Include one concrete fact or instruction.
- Link to the full context.
- Invite a specific kind of report or example when feedback is desired.
- Gratitude can name the person and the contribution.
- Avoid compressing a nuanced design dispute into a verdict.
